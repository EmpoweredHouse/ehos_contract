## Still open: argue event-driven design

**Michał's question:** "Zrobiliśmy dosyć szybki przeskok z DDD na EDD i ja chciałbym zrozumieć, jakie są
plusy." The same system is expressible in DDD terms, and either can be contracted. His reframe is the
answerable one: which do we believe a model generates better.

**What is answered.** The record now argues verifiability: `command -> {:error, reason} | [events]` is a
pure function with an enumerable output, so a model's work can be checked against an example without
running the rest of the system. And a second leg from inside the tradition — the doctrine's own source
names event versioning and the invisible event graph as unsolved, and contract-as-code plus a derived
registry answers both. The provenance is recorded honestly: the choice was instinct first, reading after.

**What is not.** The research Michał asked for. And the tension between "neither method is a moat, so do
not argue the leg on it" and "contributors buy an idea about how software is made, so we must argue it"
is now stated in the record as two different jobs — commercial differentiation and open-source
adoption — but stating it is not the same as having the argument ready for a conference stage or for a
technical lead at Allegro.

# Decisions taken, 3 August

Worked through one at a time, because the list itself was the obstacle. Each was restated as options,
what each commits to, what would settle it, and what deferring costs. What follows is the reasoning; the
decisions are in the record.

## Cross-module data access — deferred with a trigger

**The first framing here was wrong, and Emil's objection is what caught it.** It asked how far
confinement should go, database or database plus HTTP, and assumed each module would declare its
permitted tables *in the contract*. At workshop time there are no tables. It goes further than he put
it: a table list is not business meaning, so no process owner can approve it, and deriving it from the
generated schema would make part of the contract a function of the code — which the technology notes
rule out, because a contract derived from the implementation agrees with it by construction and detects
nothing. Kamil's tables-from-event-names, Michał's prefixes and Emil's "we don't have table names" were
three symptoms of one mistake: the grant was in the wrong artifact.

**The deferral argument collapsed with it.** "Cannot be retrofitted" held only while grants sat in the
contract. Take them out and it is fully retrofittable.

**The version that survives** derives the grant from module structure: a module may touch the schemas its
own boundary owns, which `boundary` and the Ecto schemas already know at compile time. No declaration
anywhere. This keeps what Michał wanted — a deterministic cut at runtime rather than a lint — and drops
the part that made it a contract extension.

**Deferred on evidence, not on principle.** No violation has been observed; the demand is an unverified
claim about what technical buyers ask, and the seat that could confirm it is Karol's; at pilot scale one
person reads every diff; and the lint already covers the ordinary case, since models generate idiomatic
Ecto rather than string SQL.

**The strongest reason came last and nobody said it in the room:** a check enforces a boundary, so it can
only be as right as the boundary is. Enforcing a wrong split turns a design problem into a production
incident. The real risk with generated code is the boundary being drawn wrongly, not crossed — so
decomposition doctrine and the pilot come first. The order is forced, not preferred.

**One thing to do now, and it is not building.** Confirm Ecto offers a middleware hook on the repo that
can see which tables a query touches — twenty minutes, Kamil. The whole deferral rests on the check being
retrofittable, and it is only retrofittable if that hook exists. If it does not, adding the check later
means changing how modules reach the repo at all, which is structural and would have to be decided now.

## Pilot — TaxVision first, Rehmed in parallel afterwards

The record's biggest unknowns are contract-shaped, and you cannot learn whether a process owner will
approve examples while also fighting an unmapped domain and a deadline.

**Two things ride along and neither is settled by the choice.**

*Parallel Rehmed against the capacity gap.* Decision 007 reduced it without closing it, workshop
facilitation is a named gap, and every month of platform work is expensive. Two implementations plus
package development is the exact shape of the *architecture became the project* falsification condition.
Not an argument against — an argument for naming who drops what if it slips.

*The generic project.* The stated intention is to start on a generic project exercising the ADR's
approach before the client work. That sits against §16–17, and the reason is not dogma: **a generic
project can test the machinery and cannot test the product.** Every falsification condition is
client-side — whether a process owner reads an example, whether the diff is signal or noise, whether the
contract costs more than the drift it catches, whether the process row fits a real business process.
What a generic spike *would* prove, that Elixir and Oban and `boundary` can be wired together, was never
in doubt. **Recommendation: make the spike one bounded TaxVision process.** That is the record's own
phrasing, costs the same, and tests the parts that can kill this. If a purely technical spike is still
wanted, timebox it and state that its output is knowledge rather than code anyone keeps — otherwise it
becomes the template §16–17 refuses to build.

## Retention — persist by default

Missing evidence is a silent product failure; excess data is visible and fixable. So a payload field
nobody marked is stored, and there is deliberately **no compile-time gate** forcing a decision on
personal-looking fields — that was recommended and declined.

*Accepted risk, recorded rather than mitigated:* with personal data the exposure is a function of **kind,
not volume**. One unmarked name field is an exposure whatever the row count, and the purge job does not
address it, because it deletes by date rather than by class.

Two mitigations belong to the decision. Volume is managed by an Oban job purging by age, which means the
**conformance window is bounded by retention** — evidence with a six-month horizon is a different promise
from evidence without one, and the client-facing wording must match what is on disk. And dashboard access
is tightly restricted with access levels, which makes the event log rather than the admin panel the first
real requirement on the permission engine.

## Log location — with the client

Their application, their database, their infrastructure; we read it to produce the evidence artifact.
Keeps the data-processing obligations, including whatever P25 turns out to require, on their side, at the
cost of hosted conformance history not being a product in v1.

Reversible on one condition, which is therefore a requirement: **the log schema assumes nothing about
where it lives.** Revisit when a client asks — and note it is a sales question, which is the third
question for Karol.

## Screens — separate frontend against a hard API boundary

Neither of the two options offered. The engine stays headless behind an API; a frontend is a separate
application consuming it, possibly built by another party; the API is the hard boundary, so an
application can do no more than the API permits.

Three consequences, none of which were in the record:

- **The API becomes a second product surface**, needing stability, versioning and documentation once a
  third party codes against it. Hand-maintained beside the contract it would be two editable
  representations of the same thing, so it is generated from the contract like the tests and dashboard.
- **The permission engine must be real from the start**, because the boundary is enforced server-side —
  a frontend someone else wrote is not trusted.
- **Build the first frontend ourselves anyway.** The pilot needs a short loop between a process owner
  approving examples and the diff being judged useful; a third party lengthens it and makes the date
  depend on someone with no stake. Outsource from the second client.

This opened a new question — **REST or GraphQL** — which is not a detail once a third party may build the
frontend. Michał argued against GraphQL in the same review on adoption grounds: with REST any developer
can maintain it, with GraphQL the pool is smaller, and an outsourced frontend makes that pool matter
more. The counter is equally real: GraphQL lets an external team fetch what it needs without asking us
for an endpoint each time. REST widens *who* can build it; GraphQL reduces *how often they need us*.
Deferred by choice.

## Identity — separate applications, identity bought

Identity is its own application (WorkOS wrapped), the engine is its own, the dashboard stays inside the
engine in v1, frontends are separate and later. This answers Michał's control-plane question by
construction rather than as an addition.

Identity is bought rather than written because SSO, the Google and Microsoft integrations, user lifecycle
and audit are commodity infrastructure and not what this leg is differentiated on. That was Michał's own
position in the meeting; the first answer here was to build it, and the recommendation to buy was taken.

**Stated explicitly in the record because it will be misread:** several applications do not overturn
one-app-one-Postgres. What §5–6 protects is a single transaction, which only ever concerned the engine.

## Failure handling — a person decides

The system detects the derailment and puts it on a human's work queue; it does not choose the recovery.
No recovery paths in the contract, no workflow language.

The condition that makes this generative rather than merely cheap: **the human's decision is issued as a
command and emits events.** A row edited by hand leaves no trace, and the log then has a hole exactly
where the interesting thing happened. Issued as commands, every exception becomes a recorded case, so the
recovery rules worth automating later are ones that were observed instead of guessed.

Cost named rather than argued away: a human per exception caps throughput at human speed, which is in
tension with the throughput case for an accounting client. That tension is what the pilot measures.

## Example size — no limit, measure corrections instead

A number invented before the first workshop would be wrong, and a check that is sometimes wrong about a
judgement call gets disabled within a month. What is measured instead is **whether the process owner
corrects anything** — thirty examples and zero corrections means nobody read them, which turns a
falsification condition into an observation. The size of `given:` is only a proxy. The heuristic, that an
example needing more than a handful of facts is usually two rules under one name, belongs in a skill.

## Event shape change — narrowed, not solved

**Emil's correction, and it was right.** The dashboard joins on event names, order, timing and process
membership and never reads a payload; a frontend always runs against the current API version and shows
current work rather than history. Neither operational surface is affected by payload evolution, and the
earlier framing here overstated it.

Where it bites is anything making a claim about the **past** from payload values: the evidence report,
reporting from the log, and the `given:` state in a durable example. Smaller and more specific — and on
the commercial side of §16–17, which is the part clients pay for.

Decided alongside: the payload is declared in the contract, stored as JSON, and read defensively.
Declared shape at write time, tolerant reading at read time. The declaration is required because
per-field retention cannot apply to an opaque blob and payload-conformance tests need something to assert
against.

Still open: what a report spanning a definition change should say. Two things bear on it. The contract
version is only trustworthy if changing a payload declaration without bumping it fails CI — cheap now,
unavailable later. And purge-by-age is an **accidental** answer, because it deletes the oldest and
therefore old-shaped events; accidental answers should be made deliberate before a client asks about a
period we quietly purged.

Genuinely unsolved, here and in the literature: a change of meaning with no change of shape. `deadline`
moving from calendar day to business day touches no declaration, so no lint, schema or JSON fallback
catches it.

# Owed

## Karol's review — three questions, needs a date

**"Review the ADR" is the wrong ask.** Eight hundred lines written for a technical owner; he is not that
reader. But his seat blocks the record's own gate — nothing material begins until all four reviewers have
been through it — so this needs a date rather than goodwill.

Three questions he answers from conversations he has **already had**, not from reading:

1. **Is the evidence artifact what a buyer asks for, or did we invent it?** Not "is it a good idea".
   Concretely: has anyone, unprompted, said something like *"I don't know whether my software does what
   we agreed"*? Or did they say cheaper, faster, this specific feature? The record's whole premise is
   that this gap is felt. If nobody has voiced it, the premise is a hypothesis. This is the falsifiable
   one and the most important.
2. **Does "code is open, you pay for the workshop and the evidence" survive procurement?** Does it read
   as consulting — day rates, no leverage — or as product? And what stops a client taking the open code
   and skipping the workshop? He is the one who will hear that objection first.
3. **What does the buyer already pay for that this displaces?** A new budget line needs a
   founder-level sponsor and a business case; displacing an existing line — an audit, a compliance tool,
   a consultancy, headcount — sells. This determines the sales motion and it is squarely his
   accountability.

Plus one cheap confirmation, now that the log lives with the client: does the market agree? If clients
want hosting, hosted conformance history returns as a product sooner than assumed.

## Prior art — five directions, owner Filip

Kamil asked what already exists, on the assumption that our value is the contracts plus the observability
guarantees. Technology notes §12 covers Elixir libraries and event formats; **nothing covers the
specification-and-verification tradition.** "Look into prior art" is not a task, so here are the
directions and the question each answers.

**1. Conformance checking — the most important.** Not a gap in our knowledge but an established
academic field: process mining, van der Aalst's school. Given a process model and an event log, compute
how well they align — real algorithms (token replay, alignment-based), real tools, thirty years of
literature. **Declared-versus-observed *is* conformance checking.** The record names Celonis as a
competitor and never engages the field. Three payoffs: we may not need to invent an algorithm that is
already described; we get vocabulary the client's analysts know; and the literature documents what "the
diff is mostly noise" looks like when others hit it — which is our own falsification condition.
*Question:* does alignment-based conformance checking give us the join, and how does our position differ
given that we control emission and Celonis does not?

**2. Specification by Example and BDD.** Adzic, Cucumber, Gherkin. §18 is the direct descendant, minus
the prose layer. The value is not what to do but that **fifteen years of documented failure describe
exactly our risk**: the glue between prose and assertion rots, the business stops reading, and the suite
becomes a slow integration test owned by QA — word for word our "examples written by developers alone and
the process owner never reads one". *Question:* what specifically made the business stop reading, and
does removing the prose layer fix that or make it worse?

**3. Design by Contract.** Eiffel, Meyer — preconditions, postconditions, invariants checked at runtime.
Literally "contract" as executable obligations. *Question, and it is the pointed one:* why did it not
win? Suspicion: the contracts lived in the code, written by developers, so nobody outside engineering
reviewed them — precisely the property we claim for ours. If so, it is an argument **for** us and worth
having named.

**4. Contract testing for APIs — newly relevant.** Pact and consumer-driven contracts. Became relevant
the moment the frontend became a separate application possibly built by a third party. Pact solves
exactly that: consumer and provider agree a contract and CI proves both honour it. *Question:* do we take
it instead of inventing how to police the API boundary?

**5. Spec-first code generation by models.** The old MDA/UML-codegen wave and the current
write-a-spec-generate-the-code tools. **Highest strategic risk, lowest confidence in what exists.** If
someone has built the contract half, that is a strategy question rather than an ADR one.

**Scope and owner.** One day for all five is optimistic; one day gets 1 and 2 properly, and those two
carry the most weight. Owner: **Filip** — decision 007 makes his development research-under-task on
topics he works on, which is exactly this. Kamil raised it, so he is the reader. Output is **not a
literature survey**: one page answering "what have others learned that changes what we do", plus a
recommendation on anything worth adopting rather than rebuilding.

## Not an ADR item — Shugyo consuming PNS

Michał: we must write a connector and design it for the maximum analysis we can extract; that is where the
two legs meet, and Shugyo plugs in once a prototype exists. Emil: expose the contract read-only plus MCP
with each endpoint as a tool. Michał is unconvinced that yields the analysis wanted. Filip's question —
one Shugyo across apps, or one per app — went unanswered. Shugyo-side work; recorded so it is not lost.
